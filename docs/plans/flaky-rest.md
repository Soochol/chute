# 남은 흔들리는 시험을 원인에서 고치는 플랜

> 작성일 2026-11-17. 플랜 에이전트가 쓴 설계다. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 1. 사용자가 풀려는 문제

flaky-ext 플랜(PR #74)을 승인할 때 사용자는 "남은 흔들리는 시험 4개도 이어서 고칠지"라는 질문에 "진행"이라고 답했다. flaky-ext(PR #77)가 main `50db7a9`에 들어간 뒤 넷을 한 플랜으로 묶는다. 흔들리는 시험은 chute batch에서 엉뚱한 PR을 반송하거나 `flaky` 기록을 늘려 머지를 늦춘다.

| 번호 | 시험 | 앞선 관찰 |
|---|---|---|
| 1 | `src/env.rs`의 `env::tests::cancelling_ends_the_running_check_and_skips_the_rest` | flaky-ext 작업자의 부하 반복(전체 `--lib` 72회)에서 4회 실패했다. 실패한 단언은 기록되지 않았다 |
| 2 | `src/env.rs`의 `env::tests::a_check_that_outlasts_the_limit_is_cut_and_the_next_one_still_runs` | flaky-two 보고서가 흔들린다고 적었다. 횟수와 단언은 없다 |
| 3 | `tests/daemon.rs`의 `a_stop_request_made_just_now_is_kept_when_the_daemon_starts` | flaky-two: main 2/64, 그 PR 뒤 3/160. `tests/daemon.rs:45`(`wait_until`이 30초를 넘김) |
| 4 | `tests/daemon.rs`의 `the_daemon_runs_gc_when_it_starts_and_leaves_the_records` | flaky-two: `:64`(`ok()`에서 `.git/worktrees/batch/commondir`을 읽지 못함)와 `:427`(정리를 기다리다 30초를 넘김) |

## 2. 확정된 결정

| 번호 | 항목 | 결정 |
|---|---|---|
| 1 | 고치는 방법 | 재현으로 원인을 찾아 원인을 고친다. 재시도, sleep 늘리기, 한도 늘리기, `#[ignore]`로 덮지 않는다 (flaky-two, flaky-ext와 같다) |
| 2 | 근거 | 고치기 전 실패율과, 고친 뒤 같은 부하에서 연속으로 통과한 횟수를 보고서에 남긴다 |
| 3 | 결함 검출 | 고친 시험이 여전히 제품 결함을 잡는지 임시로 제품을 망가뜨려 확인한다 |
| 4 | 묶음 | 넷을 한 플랜으로 다룬다 |

## 3. 플래너가 한 재현 (main `50db7a9`, 32코어, 다른 작업이 함께 돌아 load 40~50)

부하는 바쁜 루프(hog) N개와 시험 바이너리 동시 실행이다. 진단을 넣은 실험은 scratchpad의 사본에서만 했고 저장소에는 넣지 않았다.

| 실험 | 결과 |
|---|---|
| `env::tests`만. hog 40개, 동시 16개 × 5라운드 | 80회 중 실패 0 |
| 전체 `--lib`. hog 8개, 동시 6개 × 6라운드 | 36회 중 실패 0 |
| 1번. `record_within`이 검사 전에 400ms 멈추게 함 (`machine::core`가 느린 경우를 흉내) | 6/6 실패. `env.checks.len()`이 0 (`src/env.rs:359` 단언) |
| 2번. 시간 한도 300ms를 1/2/5/10/20ms로 줄임 (각 6회) | 1ms에서 1/6 실패. 둘째 검사 `echo after`가 잘려 출력이 `after (0초 안에 끝나지 않아 멈췄다)`. 2ms 이상은 통과 |
| 3·4번만(`--exact`). hog 40개, 동시 16개 × 5라운드 | 80회 중 실패 0 |
| daemon 바이너리 전체. hog 40개, 동시 16개 × 4라운드 | 64회 중 2회 실패. 둘 다 4번, `tests/daemon.rs:430` `assert!(lab.store.dir().join("gc.json").is_file())` |
| 같은 부하에 진단을 넣어 반복. 데몬이 `remove_stale_stop`에서 본 정지 파일의 나이를 기록함 | 64회 중 3번이 2회 실패(`:45`). 나이는 최소 130ms, 중앙값 385ms, 90% 880ms, 최대 2341ms. 2초(`STALE_STOP`)를 넘은 두 회가 실패한 두 회다 |
| 위 실행에서 함께 | 목록에 없던 `the_daemon_checks_the_tip_after_the_merge_beside_the_queue_and_down_ends_the_check`가 1회 실패. `post.pid`를 읽어 `parse`할 때 `ParseIntError { kind: Empty }` |

4번의 `commondir` 실패와 30초 대기 실패는 128회 안에서 다시 보지 못했다. 같은 상황에서 `git worktree list --porcelain`을 돌려 보면, `commondir`이 없거나 빈 `.git/worktrees/batch` 폴더가 있어도 실패하지 않는다(git 2.53.0). 그래서 어느 git 명령이 그 메시지를 냈는지는 아직 모른다.

## 4. 스스로 정한 결정

| 번호 | 항목 | 결정 | 이유 |
|---|---|---|---|
| A | 1번의 원인 | 시험은 300ms 뒤에 취소한다. 그런데 `record_within`은 첫 검사 전에 `machine::core`로 가짜 `hc`를 띄운다. 부하 속에서 이 일이 300ms를 넘기면 첫 검사를 시작하기 전에 취소가 오고, `take_while`이 검사를 하나도 돌리지 않는다 | 3절의 강제 재현과 실패 단언이 맞는다. 단독 실행은 통과하고 다른 시험이 프로세스를 많이 띄우는 전체 `--lib`에서만 흔들린다는 관찰과도 맞는다. 자연 실패의 단언은 작업자가 진단으로 확인한다 |
| B | 1번을 고치는 곳 | 시험이다. 첫 검사 명령이 시작했다는 표시 파일을 남기고, 멈추는 스레드는 시간 대신 그 표시를 보고 취소한다. 표시를 기다리는 단계에는 멈춤을 잡는 상한만 둔다 | 제품은 맞게 동작한다. 취소가 첫 검사 전에 오면 검사를 하나도 하지 않는 것이 맞다. 시험이 "도는 중인 검사를 취소한다"를 보려면 취소가 검사가 도는 동안에 와야 한다 |
| C | 2번의 원인 | 300ms 한도가 벽시계로 흐른다. 부하 속에서 `sh`가 `echo start`를 하기 전에 한도가 지나거나, 둘째 검사 `echo after`가 300ms를 넘겨 잘린다 | 3절의 한도 축소 실험. flaky-ext의 원인 A와 같은 꼴이다 |
| D | 2번을 고치는 곳 | `verify::run_command`가 기한을 주입된 시계로 읽는다. `Ext`의 시계(`Ext::with_clock`, flaky-ext가 만듦)를 `env::record_within`이 넘긴다. 기한은 프로세스를 띄우기 **전에** 읽는다. 시험은 멈춘 시계와 아주 긴 한도(예: 1시간)를 쓰고, 첫 검사 로그에 `start`가 보이면 시계를 한도 너머로 한 번 옮긴다. 검사 단계(`Ctx::step`)의 동작은 바꾸지 않는다 | 기한을 띄우기 전에 읽으면 "로그에 `start`가 있다"가 "기한을 이미 읽었다"보다 뒤에 온다. 그래서 시계를 한 번만 옮겨도 된다. 이 방식은 flaky-ext가 겪은 결함 3(기한을 읽기 전에 시계를 옮김)을 피하고, 둘째 검사의 기한은 옮긴 시계를 기준으로 잡혀 잘리지 않는다. 긴 한도를 쓰면 제품이 시계를 무시할 때 첫 검사가 잘리지 않아 시험이 실패한다. flaky-ext 보고서의 약점 2를 이 시험에서는 막는다 |
| E | 3번의 원인 | `chute daemon`은 시작할 때 정지 파일이 2초(`STALE_STOP`)보다 오래됐으면 지난 실행이 남긴 것으로 보고 지운다. 나이는 `remove_stale_stop`을 부르는 순간에 잰다. 시험은 정지 파일을 쓰고 데몬을 띄우므로, 나이에는 프로세스 시작과 `route`, `registered_repo`(git과 hc 호출), 잠금, `daemon.json` 쓰기까지 걸린 시간이 모두 들어간다. 부하 속에서는 이 시간이 2초를 넘는다 | 3절의 나이 측정. 2초를 넘은 회와 실패한 회가 정확히 맞는다 |
| F | 3번을 고치는 곳 | 제품이다. 정지 파일이 오래됐는지를 나이가 아니라 순서로 판정한다. 데몬은 잠금을 잡기 **전에** 정지 파일의 상태(있는지, 있으면 inode·mtime·길이 같은 식별 정보)를 읽어 둔다. 잠금을 잡은 뒤에는 그때 본 파일이 그대로 남아 있을 때만 지운다. 잠금을 잡은 뒤에 쓰였거나 바뀐 정지 파일은 남긴다. `STALE_STOP`과 나이 비교는 없앤다. 시험 3은 이 판정을 따라 고친다(아래 G) | `chute down`은 데몬이 잠금을 쥐고 있을 때만 정지 파일을 쓴다(`src/cmd/down.rs`의 `daemon_running`). 그래서 잠금을 잡기 전부터 있던 정지 파일은 앞 데몬에게 한 요청의 잔여물이다. "방금 한 정지 요청"(커밋 `2766e83`의 의도)은 새 데몬이 잠금을 잡은 뒤 `remove_stale_stop`보다 먼저 `chute down`이 쓴 요청이다. 순서로 판정하면 이 요청은 남고, 시각이나 부하에 기대지 않는다. 지금의 2초 규칙은 그 의도를 시각으로 흉내 낸 것이라, 2초 안에 시작한 데몬이 앞 데몬의 잔여 요청을 받고 바로 멈추는 일도 생긴다 |
| G | 3번 시험의 모양 | 판정 규칙은 `src/cmd/daemon.rs`의 단위 시험으로 본다. 경우는 셋이다: 전에 없던 파일이 생겼으면 남긴다, 전에 본 파일이 그대로면 지운다, 전에 본 파일이 다시 쓰였으면 남긴다. 통합 시험 `a_stop_request_made_just_now_is_kept_when_the_daemon_starts`는 새 규칙에 맞는 관찰로 바꾼다. 예를 들어 데몬이 뜬 뒤(`wait_for_daemon`) 쓴 정지 요청으로 데몬이 멈추는지 본다. 이름과 주장이 바뀌면 PR과 보고서에 적는다. `a_stop_request_left_by_an_earlier_run_does_not_stop_the_new_daemon`은 방금 쓴 잔여 파일(나이 0)로도 통과해야 한다 | 바깥에서 띄운 프로세스의 "잠금 뒤, 판정 전" 틈에 정확히 파일을 쓸 방법이 없다. 판정을 순수한 함수로 떼어 내면 그 틈을 단위 시험으로 덮을 수 있다. 제품 동작을 바꾸지 않는 시험 전용 환경 변수 같은 훅은 두지 않는다 |

| I | 4번을 고치는 곳 | 시험이다. gc가 끝났다는 마지막 관찰(`gc.json`이 생김)을 기다린 뒤 로그가 지워졌는지와 기록이 남았는지를 본다. 데몬을 띄우기 전에는 `gc.json`이 없음을 단언해서, 기다린 파일이 이 데몬의 gc가 쓴 것임을 보인다 | 제품 동작은 맞다. 사용자가 그 틈에 `chute status`를 봐도 해가 없다 |
| J | 4번의 나머지 두 실패 | 작업자가 데몬의 stderr를 파일로 남기는 진단을 넣고 같은 부하로 다시 잡아 본다. 잡히면 원인을 찾아 고친다. 동시에 도는 git 작업 때문에 chute 명령이 실패하는 제품 결함이면 제품을 고친다. 잡히지 않으면 시도 횟수와 함께 보고서의 미해결에 적는다. 진단은 커밋하지 않는다 | 3절에서 다시 보지 못했고 메시지만으로는 어느 명령인지 모른다. 원인을 모른 채 고치면 결정 1에 어긋난다 |
| K | 새로 본 흔들림 | `the_daemon_checks_the_tip_after_the_merge_beside_the_queue_and_down_ends_the_check`도 이 플랜에서 고친다. 시험이 상태(`post.run.step`)로 "검사가 시작됐다"를 본 뒤 `post.pid`를 읽는데, 스크립트의 `echo $$ > post.pid`는 그보다 늦을 수 있다. 파일이 잘린 직후를 읽으면 빈 문자열이다. 둘째 검사에서는 첫 검사가 남긴 옛 pid를 읽을 수도 있다. 그러면 `is_gone(pid)`가 아무것도 보지 않는다. 시험은 둘째 검사 전에 `post.pid`를 지우고, 스크립트는 pid를 임시 파일에 쓴 뒤 이름을 바꾼다. 시험은 이번 검사의 pid가 보일 때까지 기다린다 | 3·4번과 같은 파일, 같은 꼴(중간 상태를 끝으로 봄)이고 시험만 고치면 된다. 남겨 두면 같은 batch에서 다시 흔들린다. 사용자가 범위에서 빼려면 승인 때 알려 준다 |
| L | 작업 수 | 둘. `flaky-env`(1·2번)와 `flaky-daemon`(3·4번과 K)이다. 겹치는 파일이 없어 병렬로 둔다 | 두 묶음은 원인도 파일도 다르다. 하나로 묶으면 PR 하나에 제품 변경 둘(시간 초과 기한, 데몬 정지 판정)이 섞여 검토가 무거워진다 |

### 작업과 방식

| 작업 | 프로필 | 방식 | 이유 |
|---|---|---|---|
| `flaky-env` | `minor-fix` | `poteto` | 파일 셋(`src/env.rs`, `src/verify.rs`, `src/ext.rs`)과 시험 둘이다. 외부 프로세스의 시간 초과 기한을 바꾸므로 `basic` 조건(프로세스)에 걸린다 |
| `flaky-daemon` | `minor-fix` | `poteto` | 파일 둘(`src/cmd/daemon.rs`, `tests/daemon.rs`)과 시험 셋이다. 데몬 시작 때의 잠금 순서와 정지 요청 판정을 바꾸므로 `basic` 조건(잠금·프로세스)에 걸린다 |

순차로 둔 작업은 없다. 두 작업은 겹치는 파일이 없다.

다른 플랜과의 관계: post-recheck 플랜(PR #78, 아직 작업 전)이 `src/verify.rs`의 `Options`와 `Ctx::step`을 고친다. `flaky-env`는 같은 파일의 `run_command`와 `wait`만 고치므로 겹치는 함수가 없다. 표의 "같은 파일에 각자 몇 줄 더한다"에 해당해 병렬로 두고, `flaky-env` 지시서에 그 파일은 최소로 고치라고 적었다. 먼저 머지된 쪽 뒤에 다른 쪽이 기본 브랜치를 합친다. needs-card와 post-probe는 이미 머지됐다.

## 5. 범위 밖

- `src/env.rs`의 다른 시간 시험(`an_endless_check_is_bounded_in_time_and_log_size`)과 `tests/daemon.rs`의 다른 시험. 흔들린다는 관찰이 없다.
- 검사 단계(`Ctx::step`)의 기한을 띄우기 전에 읽게 바꾸는 것. post-recheck가 그 근처를 고치고, 흔들린다는 관찰도 없다.
- 정지 파일의 형식 변경(요청마다 고유한 값을 쓰는 등).
- flaky-ext 보고서의 미해결 둘(`pipes_close_when_the_call_returns`가 원리상 다른 스레드의 fork에 흔들릴 수 있음, 드레인으로 바뀌면 300초 멈춤).

## 6. 사용자가 정해야 하는 결정

| 번호 | 질문 | 플래너의 권고 |

| 1 | 데몬이 시작할 때 정지 파일을 지우는 규칙을 "2초보다 오래된 것"에서 "잠금을 잡기 전부터 있던 것"으로 바꿀지 (결정 F) | 바꾼다. 데몬이 없을 때 쓰인 정지 파일은 나이와 상관없이 지워지고, 데몬이 잠금을 잡은 뒤 쓴 요청은 남는다. `chute down`은 데몬이 떠 있을 때만 정지 파일을 쓰므로 사용자가 보는 차이는 없다. 시각에 기대지 않으니 시험이 흔들리지 않는다. 지금 규칙을 지키려면 시험이 바깥 프로세스의 시작 시간과 경주하는 것을 피할 길이 없다 |
| 2 | 새로 본 흔들리는 시험(결정 K)을 이 플랜에 넣을지 | 넣는다. 같은 파일에서 시험만 고치면 된다 |
